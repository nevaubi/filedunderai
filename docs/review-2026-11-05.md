# Repository and Supabase review — November 5, 2026

This review distinguishes observed production data, released application changes,
and financial maintenance that requires its own receipts. It does not treat a
successful build as proof that every historical company record is normalized.

## Financial correctness changes

Market capitalization requires a finite positive price and a valid, directly
reported outstanding-share observation. It rejects future reporting periods,
future filing availability, unsupported derivations, wrong share bases and
observations older than the configured 400-day limit. The browser and Python
paths use the same rules.

The companies job publishes its validated in-memory fundamentals snapshot instead
of immediately rereading a potentially stale storage object. Index financial
metrics are withheld for aggregate entries that have not passed normalization
version 2. Screener financial cache version 6 includes normalization and share
metadata in its cache key and does not reuse failed or legacy financial extracts.
P/E calculation no longer incorrectly depends on market-cap availability.

Free-cash-flow derivation requires matching periods and units and treats capital
expenditure as an outflow. Nonadditive EPS and weighted-share observations are
not reconstructed by subtracting cumulative periods.

### Current financial-window and share-basis corrections

Read-only preparation rebuilt the complete 800-company, 239-field screener from
stored inputs. The first candidate correctly failed its publication gates:
six capitalization mismatches, four EPS/P/E mismatches and four closing-price
serialization mismatches. It was not published.

Citigroup and NextEra had newer reported share observations in their normalized
company metadata, but the screener extraction replaced them with older archived

The current financial window is now shared across income metrics. A complete

HON 21.02 from mixed share bases. The other 15 supported EPS values are preserved;
the corrected index and screener calculations have zero EPS mismatches across
that normalized cohort.

Honeywell's June 29, 2026 spin-off and one-for-two reverse split are confirmed by
its [SEC-filed release](https://www.sec.gov/Archives/edgar/data/773840/000077384026000084/exhibit991-pressrelease629.htm).
Its [second-quarter filing](https://www.sec.gov/Archives/edgar/data/773840/000077384026000124/hon-20260630.htm)
retrospectively adjusts the share/per-share presentation. The stored selected
quarters mix older pre-event filings with that adjusted presentation, while the

one-for-two share change. Current EPS-based valuation receives a sourced hold

Historical reported observations remain inspectable. The company overview
supports the hold explanation and source links; Compare honors the same current
EPS hold. The production index inspected in this review predates that hold, so
the explanation and corrected aggregate values depend on the separately

The full comparison of shared current ratios also caught Costco's 16-week
fourth quarter. Calendar-offset lookup missed its preceding reported quarter by
one day beyond the old tolerance, withholding supported revenue, cash flow and

The publication gates now cover every financial ratio shared by the index and

The current-window refresh also rederives the top-level dividend and buyback

across the captured normalized entries. Refreshing only the nested financial
summary would have left those stale yield inputs behind. Company identity,
filing context and independently supported share metadata remain preserved.

### Full normalization remains a separate review

The broader reconstruction pilot found genuine differences between older reported
quarters and later derived alternatives. Examples included NVIDIA buybacks and
Airbnb stock compensation. The repair rejects replacing reported observations
with derived values, regressing filing dates, losing reported periods, or changing
equally dated reported values without review.

Removing demonstrated nonadditive derivations does not resolve those historical
version conflicts. Cleanup-only does not stamp a legacy bundle as version 2 or
replace unrelated reported/additive values. The remaining legacy count must be
reported from a fresh inventory rather than inferred from successful cleanup.

## Supabase access review

Catalog inspection ran in explicit read-only transactions with eight-second
statement timeouts, between 14:29:35 and 14:34:00 UTC.

| Control | Observed result |
|---|---|
| Public tables | All 45 have row-level security enabled. |
| Public data policies | 37 financial/content tables have SELECT-only client policies. |
| Client database roles | No direct login, superuser, BYPASSRLS, public-schema CREATE, or privileged inherited role. |
| Public routines | All six deny execution to anonymous and authenticated client roles. |
| Public view | `macro_series_latest` uses invoker security. |
| Auth relations | No client SELECT/INSERT/UPDATE access to the 27 inspected relations. |
| Storage | `raw` is private; `ir` and `public-data` are public downloads. No client upload/mutation policy was found. |
| Private research | Owner-scoped policies; alert updates restricted to `read_at`; settings server-maintained columns protected. |

The six RLS-enabled tables without policies are default-deny, not evidence of a
data leak. No unintended client row-write policy or executable public routine was
found in the inspected catalog.

There is a nonurgent privilege-hardening item: 40 public tables retain broad SQL
grants including TRUNCATE, MAINTAIN, TRIGGER and REFERENCES. RLS does not protect
whole-table operations such as TRUNCATE. No exposed route to those operations was
found: client roles cannot log in directly, create public routines or execute the
existing public routines. This is a defense-in-depth recommendation rather than
a demonstrated exploitable API vulnerability. Broad future-object default grants
also deserve a separately reviewed migration.

The actual PostgREST exposed-schema setting was not available from database role
settings. This review did not perform customer-session cross-user mutation tests
or establish the complete external schema surface.

Primary references: [PostgreSQL row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html),
[Supabase bucket access models](https://supabase.com/docs/guides/storage/buckets/fundamentals).

## Operational follow-up

The initial audit observed 42 ETL runs marked running, including 37 older than
two hours, and four prior Vercel 300-second timeouts in IR/insider work. A stale
status is not proof of a still-active worker. Long backfills and the one-time
screener cache rebuild should use a long-lived worker and bounded concurrency.

An IR extraction status is also not equivalent to verified financial evidence.
The inspected Apple IR set had 144 documents with unverified/partial extraction,
while Okta had 185 verified and 14 limited records among 199 documents. Raw
document availability and extraction quality should remain separately labelled.

The original data inventory included roughly 2.5 million facts, 273,625 filings,
1.66 million daily price rows, 330 macro series and 318,608 macro observations.
Those are dated audit counts, not a substitute for a post-maintenance inventory.
